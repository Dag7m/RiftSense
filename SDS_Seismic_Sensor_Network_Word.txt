1. INTRODUCTION

1.1 Purpose
This Software Design Specification (SDS) describes the design solution for the thesis project
“Seismic Sensor Network with Real-Time Monitoring, Machine Learning Classification, and Crowd-Sourced
Felt Reports.” It translates SRS requirements into an implementable design, describing architecture,
components, interfaces, data design, security, operational aspects, and design rationale.

1.2 Scope
The SDS covers the entire system end-to-end:
  - ESP32 sensor nodes and accelerometer sampling/transmission design
  - Backend service for ingestion, storage, analytics orchestration, and RBAC APIs
  - PostgreSQL + TimescaleDB schema and time-series handling
  - ML service integration for signal classification
  - Next.js frontend for monitoring, visualization, and felt reports

1.3 Definitions, Acronyms, and Abbreviations
  ESP32: Microcontroller platform used for sensor nodes
  TimescaleDB: PostgreSQL extension for time-series
  Hypertable: TimescaleDB time-partitioned table abstraction
  STA/LTA: Short-term average / long-term average triggering method
  ML: Machine Learning
  JWT: JSON Web Token
  RBAC: Role-Based Access Control

1.4 References
  - SRS_Seismic_Sensor_Network_Word.txt (SRS-SSN-RTML-FELT v1.0)
  - IEEE 1016 (Software Design Description) guidelines
  - PostgreSQL and TimescaleDB documentation

1.5 Document Overview
Sections 2–3 define design context and system architecture. Sections 4–6 provide detailed component
and data design. Sections 7–10 cover cross-cutting concerns such as security, reliability, algorithms,
and NFR-driven design. Sections 11–13 address testability, diagram placeholders for Word insertion,
traceability, and appendices.


2. DESIGN CONTEXT AND GOALS

2.1 System Context
The system collects seismic motion data from distributed sensor nodes, stores it as time-series data,
classifies signals using ML, correlates detections into events, and displays monitoring dashboards.
Crowd-sourced “Felt It” reports provide public feedback to complement sensor detections.

PLACEHOLDER (Figure 2-1): System Context Diagram
  Insert: A context diagram showing actors (Sensor Nodes, Users, Admins, ML Service) and the system boundary.

2.2 Design Objectives
  DO-1: Provide reliable real-time ingestion and persistence of sensor data.
  DO-2: Support scalable time-series queries (recent windows and historical ranges).
  DO-3: Enable event detection via heuristics and ML classification, with traceable outputs.
  DO-4: Provide secure, role-based APIs and admin control features.
  DO-5: Provide intuitive monitoring UI and simple felt-report submission for public users.
  DO-6: Ensure the design is academically verifiable and deployable in a reproducible environment.

2.3 Design Constraints and Assumptions
  - PostgreSQL + TimescaleDB is mandatory for time-series storage.
  - Sensor nodes may experience intermittent connectivity; batch submission is supported.
  - ML service may be external; backend must handle ML unavailability gracefully.
  - HTTPS is required for production; HTTP is acceptable for local development.

2.4 Design Principles and Conventions
  - Separation of concerns: ingestion, auth, admin, events, felt reports, ML integration.
  - Stateless backend API processes; persistence in DB.
  - Consistent API envelope format: success/data or success/error.
  - Secure-by-default: input validation, parameterized queries, least privilege.
  - Observability: structured logs, health checks, audit logs for admin actions.

3.1 High-Level Architecture
The architecture is a distributed, service-oriented system composed of:
  - Sensor Node Fleet (ESP32) sending data and heartbeats
  - Backend API Service (Node/Express)
  - Database (PostgreSQL + TimescaleDB)
  - ML Service (classification)
  - Web Frontend (Next.js)

4. DETAILED COMPONENT DESIGN

4.1 Sensor Node (ESP32) Design

4.1.1 Responsibilities
  - Sample accelerometer at configured sampling rate.
  - Compute basic local metrics if required (optional).
  - Transmit samples (single or batch) to backend.
  - Send periodic heartbeats including status, battery (if available), firmware version.

4.1.2 Node Modules (Recommended)
  - SensorDriver: hardware I2C/SPI access and calibration.
  - SamplingScheduler: timer-driven sample collection and buffering.
  - BufferManager: ring buffer for samples; batch packaging.
  - NetworkClient: Wi‑Fi connection management and HTTP client.
  - HeartbeatManager: periodic status reporting.
  - ConfigManager: stores node_id and backend URL; supports OTA config update (optional).

4.1.3 Data Transmission Strategy
  - Single-sample POST for low latency (optional).
  - Batch POST for efficiency and robustness under intermittent connectivity.
  - Retry with exponential backoff on network failures.
  - Timestamping: node-generated timestamps preferred; fallback to server-assigned timestamps.

  Insert: Component diagram of firmware modules and data flow.

4.2 Backend API Service Design

4.2.1 Technology and Structure
  - RESTful API implemented with Node.js/Express.
  - Layering recommendation:
      Controllers: request/response handling
      Services: business logic (detection, ML orchestration)
      Models/Repositories: database access
      Middlewares: auth, validation, rate limiting, error handling

4.2.2 Core Backend Modules
  - Auth Module: user register/login/refresh/logout, password change, profile.
  - Sensor Module: ingest data (single/batch), heartbeat, node data retrieval, aggregates.
  - Event Module: event listing, nearby search, stats, detail, detections, admin updates.
  - Felt Module: submit report, recent/nearby/stats, intensity scale reference.
  - Admin Module: dashboard, system stats, node CRUD, user management, audit logs, DB info, cleanup.
  - Timescale Initialization: migrations, extension verification, hypertable verification.

4.2.3 Cross-Cutting Middlewares
  - Validation middleware: schema-based validation for bodies/queries.
  - Auth middleware: JWT verification, optional auth, admin enforcement.
  - Rate limiting: global and sensor-specific limits.
  - Error middleware: centralized error response, consistent envelope.
  - Logging middleware: request logging with timestamp and metadata.

4.3 Database Design (PostgreSQL + TimescaleDB)

4.3.1 Database Responsibilities
  - Persist all system data reliably.
  - Support time-series operations (hypertables, chunking, aggregates).
  - Provide efficient indexing for common query patterns.

4.3.2 Key Tables (High-Level)
  - sensor_nodes(node_id, location, status, last_heartbeat, firmware, battery, timestamps)
  - sensor_data(time, node_id, x_axis, y_axis, z_axis, magnitude, sampling_rate) [hypertable]
  - events(id, event_type, confidence, magnitude_estimate, location, detected_at, status, description)
  - event_detections(id, event_id, node_id, detection_time, peak_acceleration, sta_lta_ratio, distance, arrivals)
  - users(id, email, password_hash, role, is_active, last_login, timestamps)
  - felt_reports(id, user_id, event_id, location, intensity, description, reported_at, metadata)
  - predictions(id, node_id, segment_start/end, prediction, confidence, features, model_version)
  - admin_logs(id, admin_id, action, resource_type/id, details, ip_address, created_at)

4.4 Machine Learning Service Design

4.4.1 Responsibilities
  - Accept feature vectors (and optional waveform segments) from backend.
  - Return prediction label (earthquake/noise/unknown) and confidence score.
  - Provide model version metadata and optionally processing time.

4.4.2 ML Service Endpoints (Recommended)
  - POST /predict: input features -> output prediction + confidence + version
  - POST /batch_predict (optional): multiple segments for offline evaluation
  - GET /health: liveness check

4.4.3 Failure Handling
  - Backend must treat ML failures as non-fatal; proceed with heuristic-only decision path if required.
  - Store ML errors in logs; optionally store “ML unavailable” flags with detections.

6. DATA DESIGN

6.1 Conceptual Data Model
Key relationships:
  - sensor_nodes 1..* sensor_data
  - events 1..* event_detections
  - users 1..* felt_reports (optional)
  - events 0..* felt_reports (optional linkage)
  - sensor_nodes 1..* predictions

PLACEHOLDER (Figure 6-1): Conceptual Data Model Diagram
  Insert: High-level ER diagram (entities + relationships).

6.2 Logical Schema Overview
The logical schema mirrors the conceptual model and includes constraints such as:
  - Unique node_id for sensor_nodes
  - Primary key (time, node_id) for sensor_data
  - Foreign keys to enforce referential integrity

6.3 Time-Series Storage Strategy
  - sensor_data is a TimescaleDB hypertable partitioned by time.
  - Chunk interval chosen based on expected data rate (default: 1 day).
  - Continuous aggregates for hourly summaries.

6.4 Indexing and Aggregation Strategy
Indexing principles:
  - Index by node_id for fast per-node queries.
  - Index by time for recent-window scans (Timescale helps via chunk pruning).
  - Additional indexes for event queries (detected_at, status, type).
Aggregates:
  - Hourly continuous aggregate view per node (avg/max/min magnitude, count).

6.5 Data Retention and Cleanup
  - Raw sensor_data retention via a cleanup job or admin-triggered operation.
  - Events and felt_reports retained longer for analysis and thesis evaluation.
  - Backup strategy described in Section 8.5.


7. SECURITY DESIGN

7.1 Authentication
  - JWT-based access tokens for API authentication.
  - Refresh tokens for session continuity.
  - Password hashing via a strong one-way hash (bcrypt or equivalent).

7.2 Authorization (RBAC)
Roles:
  - Anonymous: public endpoints + felt report submission (optional auth)
  - User: authenticated endpoints for profile and user features
  - Admin: privileged endpoints for node management, logs, cleanup, event moderation

PLACEHOLDER (Figure 7-1): RBAC Matrix
  Insert: Table mapping roles to endpoint groups and permissions.

7.3 Data Protection and Privacy
  - TLS (HTTPS) in production to protect tokens and data in transit.
  - PII minimization: felt reports may store minimal identifying data; IP/user agent only as needed for abuse prevention.
  - Principle of least privilege for DB user accounts (if deployed beyond local development).

7.4 Threat Model Summary and Controls
Threats and mitigations:
  - Injection (SQL/NoSQL): parameterized queries + input validation.
  - Credential stuffing: rate limiting + password policy.
  - Token theft: HTTPS + token expiration + refresh rotation (recommended).
  - Abuse of public endpoints: rate limiting and validation.
  - Tampering with admin actions: audit logs + admin-only access.

  - Admin actions stored in admin_logs with metadata.

8. RELIABILITY, OBSERVABILITY, AND OPERATIONS

8.1 Error Handling Strategy
  - Use consistent error response format with HTTP status codes.
  - Distinguish validation errors (4xx) from server errors (5xx).
  - Avoid leaking sensitive data in error messages.
  - Graceful degradation: ML failures do not crash ingestion pipeline.

8.2 Logging Strategy
  - Request logs: method, path, timestamp, request metadata.
  - Application logs: key events (node heartbeat, ingestion success/failure, detection triggers).
  - Error logs: stack traces (server-side), correlation IDs if implemented.

8.3 Health Checks and Monitoring
  - /health endpoint for server liveness.
  - Database readiness check at startup.
  - (Optional) /metrics endpoint for Prometheus-style monitoring in future enhancement.

8.4 Rate Limiting and Abuse Protection
  - Global API rate limits for public endpoints.
  - Additional limits for sensor ingestion endpoints.
  - Optional IP-based throttling for felt reports.

8.5 Backup and Recovery
  - Development: Docker volume backup procedures.
  - Production: Scheduled database backups (logical dumps or physical backups).
  - Recovery plan: restore DB, re-run migrations, validate hypertables/aggregates.

9. ALGORITHMS AND DECISION LOGIC

9.1 Signal Preprocessing and Magnitude
  - Magnitude computed as sqrt(x^2 + y^2 + z^2) (stored per sample).
  - Optional filtering (future): moving average, high-pass filter, calibration offsets.

9.2 STA/LTA Triggering
  - Compute STA/LTA ratio over a recent window of magnitudes.
  - Trigger event detection if ratio exceeds threshold.
  - Parameters: STA window length, LTA window length, trigger threshold.

PLACEHOLDER (Figure 9-1): STA/LTA Illustration
  Insert: Diagram showing STA and LTA windows over a sample waveform/magnitude series.

9.3 ML Feature Extraction and Classification
  - Feature extraction from recent window (e.g., max magnitude, variance, spectral features).
  - ML service returns prediction label and confidence.
  - Store prediction with features and segment timestamps.

9.4 Event Correlation and Confidence Aggregation
  - Correlate detections across nodes by:
      - time proximity (within a configured window)
      - spatial proximity (within a configured radius)
  - Aggregate confidence:
      - simple averaging or weighted method (future enhancement)
  - Update event status: pending -> confirmed/false_positive via admin or rules.

10. DESIGN FOR NON-FUNCTIONAL REQUIREMENTS

10.1 Performance
  - Use Timescale hypertables and chunk pruning for efficient time-range queries.
  - Use continuous aggregates for dashboards.
  - Apply indexing strategy to reduce query costs.
  - Limit response payload sizes with pagination and limits.

10.2 Scalability
  - Stateless backend enables horizontal scaling.
  - DB scaling via tuning, partitioning (Timescale), and caching (optional future).
  - Batch ingestion reduces request overhead at high sensor counts.

10.3 Availability and Fault Tolerance
  - Retry DB connection at startup; fail fast if DB down.
  - Sensor nodes buffer data locally during outages; submit later as batches.
  - ML outages do not stop ingestion (fallback to heuristic-only).

10.4 Maintainability and Extensibility
  - Modularize backend by feature (auth/sensors/events/felt/admin).
  - Use configuration via environment variables.
  - Maintain clear API contracts and validation schemas.

10.5 Usability and Accessibility
  - Provide clear dashboards, consistent navigation, and simple felt-report submission.
  - Provide intensity scale guidance and form validation feedback.
  - Provide accessible color and typography choices (WCAG-aligned where feasible).


11. TESTABILITY AND VERIFICATION APPROACH
